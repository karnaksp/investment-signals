# Маршрут LLM через VPN

Анализ торговых сигналов, карточек позиций, консультации бота и поиск новостей
используют общий сетевой маршрут. Адрес прокси задаётся окружением.

Для Docker Desktop на текущем Mac локальный VPN-клиент доступен через
HTTP CONNECT на порту 17899. В `.env` задаются

```dotenv
GEMINI_HTTPS_PROXY=http://host.docker.internal:17899
GEMINI_REQUIRE_PROXY=true
```

При включённом `GEMINI_REQUIRE_PROXY` отсутствие адреса блокирует создание
клиента. Ошибка подключения к прокси возвращается вызывающему коду.
Все попытки к основной и резервным моделям используют указанный прокси.
Проверка TLS для целевого API остаётся включённой.

## Изменение маршрута

Замените `GEMINI_HTTPS_PROXY` адресом нового VPN-прокси и примените окружение
к процессам анализа и расписаний

```bash
docker compose up -d --no-deps --no-build --force-recreate delivery-worker dagster-daemon
```

Переменные `HTTP_PROXY`, `HTTPS_PROXY` и системный proxy не переопределяют
явно заданный маршрут LLM.

## Локальный VPN-клиент

Отдельный Xray-клиент запускается через LaunchAgent
`com.karnaksp.investment-signals.llm-egress`. Его HTTP-вход слушает только
`127.0.0.1:17899`. Профиль хранится с правами `0600` в
`~/.local/share/investment-signals/llm-egress/config.json`.

Профиль задаёт вход на HostVDS, после которого используется настроенный на
сервере VPN-выход в США. Учётные данные хранятся в локальном профиле.

При замене VPN-узла обновите профиль и перезапустите клиент

```bash
launchctl kickstart -k "gui/$(id -u)/com.karnaksp.investment-signals.llm-egress"
```

Если локальный адрес прокси сохранился, приложение продолжит использовать его
при следующих запросах. Автозапуск действует после входа пользователя в macOS.

## Проверка

Проверяйте внешний адрес и страну через прокси, а затем выполняйте настоящий
запрос к Gemini из контейнера worker. Проверка доступности TCP-порта подтверждает
только работу локального входа. Секреты VPN и ключ Gemini выводить в журнал
или сохранять в репозиторий нельзя.
