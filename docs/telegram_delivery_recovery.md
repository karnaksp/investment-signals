# Восстановление Telegram-доставки

Delivery worker разрешает адрес Telegram перед каждой отправкой. Если один из
полученных DNS-адресов не принимает TCP-соединение, worker пробует следующий.
IP-адреса Telegram в коде и конфигурации не фиксируются. TLS-сертификат всегда
проверяется для имени `api.telegram.org`.

Повтор на другом адресе выполняется только при ошибке установления TCP-соединения
до TLS и HTTP. После начала HTTP-обмена автоматическое переключение адреса
запрещено, поскольку результат запроса уже может быть неоднозначным и повтор
способен создать дублирующее уведомление.

## Ручной повтор dead-letter

Сначала выполните безопасный просмотр одной записи:

```bash
python -m tinvest_signal_engine.services.delivery_dead_letter_retry \
  00000000-0000-0000-0000-000000000000
```

Команда не показывает содержимое уведомления, токен или идентификатор чата.
Результат `eligible` означает, что запись имеет состояние `dead_letter`, а
причина относится к временной сетевой ошибке, таймауту, HTTP 429 или HTTP 5xx.

Для постановки этой же записи в очередь нужно явно повторить её UUID:

```bash
python -m tinvest_signal_engine.services.delivery_dead_letter_retry \
  00000000-0000-0000-0000-000000000000 \
  --confirm-retry 00000000-0000-0000-0000-000000000000
```

Операция:

- обрабатывает только одну запись;
- атомарно проверяет прежнее число попыток и код ошибки;
- не повторяет ошибки конфигурации и постоянные HTTP 4xx;
- сбрасывает счётчик транспортных попыток перед возвратом в очередь;
- не изменяет уже доставленные уведомления.

Если состояние изменилось между просмотром и подтверждением, команда возвращает
`conflict` и ничего не меняет.
